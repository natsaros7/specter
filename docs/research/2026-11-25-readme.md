# What makes a good README for a developer tool (research, 2026-11-25)

Input for rewriting specter's `README.md`. Two readers: a developer deciding whether to adopt specter, and someone judging the maintainer's engineering. Guidance pages, five studies and twelve READMEs. "[read]" = primary page read; "[snippet]" = search summary only: verify before citing in a decision row. Every study is correlational: a README feature that goes with more stars does not cause them.

## Guidance

| Source | What it says |
|---|---|
| GitHub Docs, "About READMEs" [read] | A README says what the project does, why it is useful, how to get started, where to get help, who maintains it. It holds "only information necessary for developers to get started using and contributing"; longer docs go elsewhere. Use relative links (absolute ones break in clones); content past 500 KiB is truncated |
| GitHub Docs, community profile [read] | The checklist looks for README, CODE_OF_CONDUCT, LICENSE, CONTRIBUTING and issue templates. SECURITY.md is documented separately: supported versions and how to report a vulnerability [read] |
| Make a README [read] | Name, description, badges, visuals, install, usage ("show the expected output if you can"), support, roadmap, contributing, authors, license, project status. "Too long is better than too short", but move the overflow to separate docs |
| Standard Readme spec [read] | Required: title, short description (under 120 characters, matches the GitHub description), install and usage code blocks, contributing, license as the last section. A table of contents is required past 100 lines. No broken links; code examples linted like the rest of the code |
| Art of README (Kira, hackergrrl) [read: a fork; the original repo returns 404] | Cognitive funnel: the broadest, most relevant facts first, details lower, background and credits last. Order: name, one-line description, usage, API, install, license. State caveats and limitations up front. Don't carry critical information only in images. Ask of every badge what it gives the typical reader |
| Diátaxis [read] | Four kinds of docs: tutorial (learning), how-to (a task), reference (facts), explanation (why). Mixing them "is at the heart of a vast number of problems." A README is a landing page: one short tutorial (the try-it block) plus links to the other three; it should not hold reference or long explanation |
| OpenSSF Best Practices, passing criteria [read] | `description_good`: say what the software does and what problem it solves. `interact`: how to get it, report bugs, contribute. `vulnerability_report_process`: publish how to report vulnerabilities |
| OpenSSF Scorecard checks [read] | Machine-checked trust: CI-Tests, Code-Review, Branch-Protection, Security-Policy, License, Pinned-Dependencies, Token-Permissions, Signed-Releases, Maintained, among 20 checks |

## Studies

| Study | Data | Finding |
|---|---|---|
| Prana et al., "Categorizing the Content of GitHub README Files", EMSE 24(3) 2019 [read] | 4,226 sections from 393 READMEs, hand-labelled | 97.0% of READMEs say *what*, 88.5% *how*; only 25.7% say *why* (purpose) and 21.4% *when* (status, version). Contribution 27.8%, references 60.8%. Classifier F1 0.746. Of 20 professionals, 12 preferred labelled READMEs, 6 neutral, 2 the unlabelled |
| Liu, Noei, Lyons, "How README Files are Structured in Open Source Java Projects", IST 2022 [read] | 14,901 Java repos; 11,594 English READMEs | Most READMEs do not follow GitHub's guidelines; those that do get more stars. Present in: description 41%, usage 31%, install 21%, license 13%, contributing 5%, ToC 2%. Effect on stars (Cohen's d): contributing 0.415 (median 9 stars vs 2), usage 0.314, install 0.311, ToC 0.219, description 0.039. 32 structure clusters; the most common ones go with less popular repos |
| Wang, Wang, Chen, "Study the Correlation Between the readme File of GitHub Projects and Their Popularity", JSS 2023 [read] | 5,000 repos, 20+ languages, popular = 50+ stars | Popular vs not (Cliff's d): time since last README update 0.91, update interval 0.90, number of updates 0.69, links 0.67, length 0.63, images 0.41, lists 0.39, code blocks 0.26, badges 0.26. After controlling for topics, licence and language, lists and update frequency matter most (random forest AUC 0.98). Popular repos mostly update references; unpopular ones rewrite usage |
| Venigalla, Chimalakonda, "An Empirical Study On Correlation between Readme Content and Project Popularity", 2022 [read: abstract] | 1,950 READMEs, 10 languages | Popular READMEs use lists, images and external links; contribution guidelines and references go with higher popularity |
| Trockman, Zhou, Kästner, Vasilescu, "Adding Sparkle to Social Coding: Repository Badges in npm", ICSE 2018 [read: project page] | 294,941 npm repos, survey and time series | 46% use a badge; 88 badge types. *Assessment* badges backed by a running analysis (CI, coverage, dependency freshness) go with better practice: fresher dependencies, more PRs with tests. Adopting a badge does not raise popularity for long. Among popular packages, many badges go with *lower* popularity |
| Marlow, Dabbish, "Activity Traces and Signals in Software Developer Recruitment and Hiring", CSCW 2013 [read] | 7 employers and 6 job seekers interviewed (from 128 survey replies) | Employers trust cues that are costly to fake and cheap to verify (the code, effort across projects) over claims on a resume. The signalling-theory split, *assessment* vs *conventional* signals, is the same one Trockman finds in badges |
| Mynampaty et al., "Linting Style and Substance in READMEs" (LintMe), arXiv 2603.00331 [read: abstract] | Design probe, user study N=11 | README checks split into programmatic ones (broken links) and judgement ones (jargon, via an LLM). Users found a small check language workable. The split matches the checklist below |

Practitioner posts on hiring-manager README scans [snippet] repeat "pitch and proof first, setup later" and cite figures (7-second scans, "48% of hiring managers read docs") with no traceable study. Not used here.

Astro and Supabase were also read: both are navigation hubs (install line, then links and package tables) and fit products with a docs site, which specter does not have.

Patterns: the first screen is a one-line *what* plus the thing it replaces or resembles (ripgrep, fd, uv, Ruff, just). Proof is something the reader can re-run (benchmarks with method, a runnable snippet, a linked measurement), not a superlative. Badges number 2 to 6. All 12 say what the tool is before how to install it; only htmx and Biome reach an install command on the first screen. Only ripgrep has a full "when not to use this" section, and it is the most cited example of a trustworthy README.

## Anti-patterns, with the evidence

| Anti-pattern | Evidence |
|---|---|
| A wall of badges | Trockman: many badges go with lower popularity among popular npm packages; Art of README: ask what each gives the reader |
| Badges that assert rather than measure ("works with X", "speed: fast") | Trockman: only assessment badges track better practice; Marlow: conventional signals are discounted |
| Claims nobody can check ("most loved", "200–300% faster") | Marlow: costly-to-fake, cheap-to-verify cues win; FastAPI has to footnote its own figures |
| Stale content | Wang: README recency has the largest effect of any factor (Cliff's d 0.91) |
| Critical facts only in images or GIFs | Art of README; screenshots also go stale silently |
| Install before the what and why | All 12 exemplars put the what first; Prana: *why* is the section most READMEs lack |
| Reference material in the README | Diátaxis; GitHub: "only information necessary to get started" |

## Trust signals for a tool that gates what merges

Specter installs a git hook, writes agent rules and, since 0.7, decides which changes a human must review. That puts it closer to a security tool than to a formatter. What the evidence supports:

- **Re-runnable proof over badges.** A two-minute block whose commands produce the claimed result, including one that fails on purpose. Specter has one; it should state the expected exit code of each line.
- **A CI badge only if CI exists.** Specter's gates run locally (`sh tests/selftest.sh`) and CI needs the maintainer's OK (v061 task 18). Saying "gates run offline, here is the command" is an assessment signal; a badge with nothing behind it would be a conventional one.
- **SECURITY.md** with supported versions and a reporting channel (GitHub, OpenSSF `vulnerability_report_process`, Scorecard Security-Policy). Specter has none.
- **A threat model in one table**: what the trust layer guards (the profile is read at the base commit, evidence comes from merged history) and what it does not (an agent with push rights, a repo that disables the hook, tiers set wrong by the human). Ripgrep's "Why shouldn't I" is the model for tone.
- **Data flow stated**: specter already says "sends nothing anywhere"; it belongs in the limits section, not only in the FAQ.

## SHOW tested against the evidence

SHOW (Story, How, Output, Worth) is a framing for portfolio READMEs read by hiring managers. For a tool README:

| Letter | Holds? | Evidence | For specter |
|---|---|---|---|
| Story | Partly. The *problem* belongs on the first screen; a narrative does not | GitHub "why useful"; Prana: only 25.7% of READMEs say why, so stating it sets a README apart. No exemplar opens with a story; they open with one line | One problem sentence ("agents cite code that doesn't exist"). The origin story (a multi-service production system, Kiro) goes to credits or `PHILOSOPHY.md` |
| How | Yes, as *how to try* and *how to adopt*. *How it works* inside goes to the docs | Liu: usage d=0.314, install d=0.311; Make a README: expected output; Diátaxis: explanation lives elsewhere | The try-it block and the GO line. Architecture: link `docs/overview/` |
| Output | Yes; the strongest-supported letter, if the output can be re-run | Marlow and Trockman: assessment signals; uv, ripgrep, Biome lead with measured output | The lint demo, failing on purpose; the report; the trust-layer screenshots whose raw text sits next to them |
| Worth | Only as "when to use it, and when not". As claimed impact, it is the marketing anti-pattern | ripgrep's "Why shouldn't I"; Art of README caveats up front; OpenSpec's and FastAPI's unverified claims | The comparison table plus a limits section |

What SHOW leaves out, and the studies weigh: **contributing** (largest effect in Liu, d=0.415), **status and version** (Prana: only 21.4% say *when*), **licence**, and **stated limits**. SHOW is a usable test for the first screen, not an outline for the whole README. For the second reader, the maintainer's engineering shows best through things they can inspect cheaply: gates, the citation lint failing on purpose, specter's own `.specs/`, dated research like this file. Marlow's employers looked for exactly that.

## README checklist for specter

**M** = `tests/gates.sh` can check it mechanically: one `python3 -I` stdlib script for every static check (one process), plus one process per try-it command. `tests/gates.sh` is planned in v061 (design: G1–G4 in order, `G<n> rc=<rc>`), not yet in the tree. **R** = needs a reviewer.

| # | Check | How | M/R |
|---|---|---|---|
| C1 | Every relative link and image resolves, including `#anchors` in `.md` targets | Parse `](…)`, `src=`, `href=`; `os.path.exists`; anchors against GitHub-style heading slugs | M |
| C2 | Every image has non-empty `alt` text | Regex on `<img>` and `![]()` | M |
| C3 | Every command in the try-it block runs and exits with the code stated beside it (`# exit 1`), and the citation lint reports more than 0 citations | Run each line from a temp clone, compare rc and a count | M (4 launches) |
| C4 | The try-it block uses no OS-specific command (`open`, `pbcopy`) without an alternative | Denylist regex | M |
| C5 | Any version named in the README equals `VERSION`; the version badge reads tags, not Releases, or Releases are current | Regex `\d+\.\d+\.\d+` vs `VERSION`; badge URL is `github/v/tag` | M |
| C6 | Anchors that carry a version (`#autonomy-profile-060`) point at the feature's current section | Covered by C1 once headings drop the version | M |
| C7 | Sections exist: Try it, Set it up, How it compares, Limits, Security, Contributing, License (last) | Heading list | M |
| C8 | The first 25 non-badge lines contain the problem sentence, the audience ("existing codebases", "any coding agent") and a proof element (the demo image or try-it block) | Presence of a marked tagline, an `<img>` and a fenced block before line 25 | M for presence; R for whether they say the right thing |
| C9 | At most 4 badges, and each is an assessment badge or licence/version | Count `img.shields.io`; allowlist of badge kinds | M |
| C10 | Short description under 120 characters and equal to the GitHub repo description | Length check; repo description needs `gh` (network): run in the release chore, not the gate | M (release chore) |
| C11 | SECURITY.md exists with supported versions and a reporting channel, and the README links it | File and heading check | M |
| C12 | The agent table's status words match the badge and prose (no "works with X" for best-effort X) | Compare agent names in the badge with rows marked ✅ | M |
| C13 | README under 200 lines; reference material (all config keys, every script flag) lives in `docs/reference.md` | `wc -l`; no `spec-kit.json` key list in the README | M for length; R for placement |
| C14 | Every number or comparative claim ("twice", "2 minutes", "about 20 minutes") links to its evidence or a command that reproduces it | Flag digits and comparatives in prose without a link on the same line | M flags, R judges |
| C15 | Screenshots are generated by a recorded command with raw text beside them, at a named commit | Each image under `docs/` has a sibling `.txt` or a source note | M |
| C16 | The limits section says when *not* to use specter, what the trust layer does not protect against, and what leaves the machine | — | R |
| C17 | No marketing words: superlatives, "blazing", "seamless", "powerful", "most loved" | Denylist regex | M flags, R judges |
| C18 | The comparison with Spec Kit, OpenSpec and Kiro is fair and current (their forms and runtimes as of the release date) | — | R, each release |
| C19 | A reader new to specter can say after the first screen what it does, who it is for and how to try it | Cold read by someone outside the project, or a fresh-context agent with only the first screen | R |

Cost: C1, C2, C4–C9, C11–C15 and C17 fit in one stdlib script reading a handful of files, well under a second. C3 adds four short processes. C10 needs network, so it belongs in the release chore.

## Proposed outline for specter's README

1. **Logo, name, one line** (problem plus audience), at most 4 badges: licence, version from tags, Python stdlib.
2. **Problem and proof** (3–4 lines): agents cite code that doesn't exist; specter makes them cite `path:line` and a lint fails the build; built for existing codebases. The lint-demo image with its alt text.
3. **Try it in 2 minutes, no install**: the four commands, each with its expected exit code; a cross-platform way to open the report.
4. **Set it up on your project**: the GO line, what the agent asks, time, what to commit. Manual install line.
5. **What it does on every change**: the loop table, plus the **trust layer** in five lines: risk label per change, when a human must review, autonomy earned from merged history, a link to `docs/overview/`.
6. **How it compares**: the current table, then "when to pick something else".
7. **Limits**: when not to use it; what the trust layer does not protect against; best-effort agents; data flow (nothing leaves the machine).
8. **Security**: link SECURITY.md; what the installer writes (hook, marker blocks) and how to see it first (`--dry-run`).
9. **Docs**: one line each for reference, method, pipeline, chores, overview and research.
10. **FAQ**: keep the model question with a link to its evidence; drop answers now covered by Limits.
11. **Contributing**: gates, offline, one command; specter is built with specter (link `.specs/`).
12. **License and credits** (last).
